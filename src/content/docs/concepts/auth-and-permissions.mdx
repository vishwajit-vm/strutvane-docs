## The office keycard analogy

Picture an office building:

| In the office | In Strutvane | Example |
|---|---|---|
| Showing your ID at the front desk | **Authentication** (signing in) | Email and password, Google, Microsoft, a passkey |
| Your keycard | Your **session** or **token** | Proves you're signed in on every request |
| Your job title | Your **role** | `admin`, `manager`, `member`, `viewer` |
| Which doors your card opens | **Permissions** | `invoice.view`, `invoice.approve` |
| Special rules on a door | **Policies** | "Managers can approve invoices, but only up to 10,000" |
| The security camera log | The **audit log** | "Ana approved INV-42 at 14:03" |

## Authentication: who are you?

Today, `@strutvane/auth` signs people in with **email and password** through a hardened adapter for [Better Auth](https://www.better-auth.com/), with secure sessions, password reset and rate limits against password guessing. An in-memory engine is included for development and tests. See [@strutvane/auth](../../packages/auth/) for the setup.

<Aside type="note" title="Planned">
Magic links, Google, Microsoft and GitHub sign-in, **two-factor authentication** and passkeys, company **single sign-on** (OIDC and SAML), SCIM, API keys, and the ready-made sign-in screens (login, register, forgot password, profile) come in later releases.
</Aside>

## Permissions: what may you do?

Every model automatically gets a set of permissions:

```text
invoice.viewAny   see the list of invoices
invoice.view      open one invoice
invoice.create    create an invoice
invoice.update    edit an invoice
invoice.delete    delete an invoice
invoice.restore   bring back a deleted invoice (with soft deletes)
```

Your own actions get one too, like `invoice.approve`, and custom routes can require any permission, like `report.revenue`.

## Roles: bundles of permissions

A role is a named group of people, like `accountant` or `manager`. Each signed-in **actor** (the person or program making the request) carries a list of roles, and policy rules say what each role may do:

```ts
allow(['viewAny', 'view', 'create'], { role: ['admin', 'accountant'] })
allow('approve', { role: 'admin' })
```

That gives this "who can do what" table:

```text
permission         admin   accountant   viewer
invoice.view         ✔         ✔          ✘
invoice.create       ✔         ✔          ✘
invoice.approve      ✔         ✘          ✘
```

<Aside type="note" title="Planned">
Roles stored in the database, `pnpm sv auth:role:create` and a printed permission matrix (`pnpm sv auth:matrix`) come in a later release.
</Aside>

## Policies: rules with conditions

Sometimes "has the permission" isn't enough. **Policies** add conditions:

```ts title="app/policies/invoice.policy.ts"
import { definePolicy } from '@strutvane/auth'
import { policySchema } from '@strutvane/framework'
import { Invoice } from '../models/invoice.model.ts'

export default definePolicy('invoice', { schema: policySchema(Invoice) }, ({ allow, deny, field }) => {
  // Accountants and managers can see all invoices
  allow(['viewAny', 'view'], { role: ['accountant', 'manager'] })

  // Anyone can see and edit invoices they own
  allow(['view', 'update'], { when: ({ actor, row }) => row.ownerId.eq(actor.id) })

  // Managers can approve invoices up to 10,000; directors can approve any
  allow('approve', { role: 'manager', when: ({ row }) => row.amount.lte(10_000) })
  allow('approve', { role: 'director' })

  // Nobody can delete a paid invoice (a "deny" always wins)
  deny('delete', { when: ({ row }) => row.status.eq('paid'), name: 'paid-is-final' })

  // Only managers and directors can see the internal notes field
  field('internalNotes').readable({ role: ['manager', 'director'] })
})
```

The `schema` tells the policy which columns exist and their types. `policySchema(Invoice)` builds it from your model, so a typo like `row.amout` **doesn't compile**. (Without the framework, describe the table with `defineSchema()` instead.)

**Three rules to remember:**

1. **Deny by default.** If no rule allows something, it's not allowed.
2. **Deny wins.** If one rule allows something and another denies it, it's denied.
3. **Lists are filtered too.** The condition `row.ownerId.eq(actor.id)` doesn't just block opening one invoice. It also means the invoice *list* only contains your own invoices. Strutvane turns the rule into a database query, so nothing leaks.

## "Why was this denied?"

Strutvane can explain any decision, rule by rule:

```ts
import { createPermissionProvider } from '@strutvane/auth'

const permissions = createPermissionProvider([invoicePolicy])
const why = permissions.explain(ana, 'invoice.approve', { type: 'invoice', record: invoice42 })

why.decision // { allowed: false, reason: 'default-deny' }
why.rules    // each rule, and whether it covered this case
```

<Aside type="note" title="Planned">
The same explanation from the terminal, `pnpm sv auth:explain --actor ana@acme.test --action invoice.approve --resource invoice:42`, comes with the auth CLI commands in a later release.
</Aside>

## The screens respect it too

If you can't delete an invoice, you won't see a Delete button. The API checks every request independently as well, so a hidden button is never the only protection.
