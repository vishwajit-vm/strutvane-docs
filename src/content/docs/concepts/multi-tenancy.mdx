Shared-database tenancy with row-level security is implemented in `@strutvane/framework` and `@strutvane/auth` `0.1.0-next.0`. The other strategies are **Planned**, and marked as such below.

## The apartment building analogy

You're building a SaaS app: many **companies** sign up and use it. Each company is a **tenant**.

Think of an apartment building:

- The **building** is your app.
- Each **apartment** is one tenant (one customer company).
- Tenants share the building, with the same lifts and the same plumbing (your code and servers).
- But nobody can walk into somebody else's apartment and read their mail (their data).

**Multi-tenancy** is the set of locks that makes this safe.

## When do you need it?

| Your app | Multi-tenant? |
|---|---|
| An internal tool for one company | No |
| A SaaS product many companies sign up for | **Yes** |
| A portal where each client company sees only its own orders | **Yes** |

You can answer "no" when you create a project and switch it on later.

## Turning it on

Mark a model as belonging to a tenant:

```ts title="app/models/invoice.model.ts" ins={3}
export const Invoice = defineModel('Invoice', {
  /* fields */
}, { tenant: true })
```

That's it. Strutvane:

1. adds a `tenant_id` column to the table, and makes `.unique()` fields unique **per tenant**
2. automatically limits every query to the current tenant, and fills in the tenant on create
3. adds a **database-level lock** (on PostgreSQL) as a second line of defence
4. answers `404` for another tenant's records, exactly as if they didn't exist, so nobody can even find out they're there

A tenant id sent in the request body is ignored, and a `belongsTo` link to another tenant's record is refused.

## How does Strutvane know which tenant you are?

`@strutvane/auth` checks a list of **resolvers**, in order, and uses the first answer:

```ts
import { headerResolver, sessionResolver, subdomainResolver } from '@strutvane/auth'
import { authMiddleware } from '@strutvane/auth/hono'

app.use(authMiddleware({
  engine,
  tenancy: { resolvers: [subdomainResolver(/* … */), headerResolver(/* … */), sessionResolver()] },
}))
```

| Resolver | Example |
|---|---|
| `subdomainResolver` | `acme.yourapp.com` → tenant "acme" |
| `pathResolver` | `yourapp.com/t/acme/…` → tenant "acme" |
| `headerResolver` | `X-Tenant-Id: …`, for trusted services only |
| `sessionResolver` | The company the signed-in user picked |

If the signed-in person isn't a member of the tenant they asked for, the request is refused with `403`. New projects created with `--tenancy` list the order in `.env` as `TENANCY_RESOLVE=subdomain,header,session`.

## Three ways to separate data

| Strategy | Analogy | Best for |
|---|---|---|
| **Shared** (the default) | Everyone in one building, with locked apartment doors | Most SaaS apps. Thousands of small tenants. |
| **Schema per tenant** (Planned) | One floor per company | Hundreds of mid-size tenants |
| **Database per tenant** (Planned) | A separate building per company | Big enterprise or regulated customers who need full separation |

Only **shared** is built today. The other two, and mixing them (most tenants shared, your biggest customer in its own database), are planned.

## Two locks, not one

On PostgreSQL, Strutvane uses two independent protections:

1. **The app's own filter.** Every query includes "only this tenant's rows".
2. **Row-level security (RLS) in the database.** Even if a bug skipped the first filter, the database itself refuses to return another tenant's rows.

```sql
-- what the database lock looks like (Strutvane writes this into your migration)
ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE ROW LEVEL SECURITY;
CREATE POLICY "tenant_isolation" ON invoices AS RESTRICTIVE FOR ALL
  USING ("tenant_id" = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK ("tenant_id" = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

The tenant is set **inside each transaction**, so a pooled database connection can never carry one tenant's setting over to the next request. `tenancyAudit()` checks for tables without the lock and for database roles that could bypass it.

<Aside type="note">
SQLite (and MySQL, once supported) don't have row-level security. There, Strutvane uses the app filter only. For production multi-tenant apps, use PostgreSQL.
</Aside>
