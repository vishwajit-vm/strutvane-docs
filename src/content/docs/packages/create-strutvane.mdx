- How to create a new Strutvane project in one command
- The three presets, and every option
- What gets generated, and the safety promises the starter keeps

<Aside type="caution" title="Pre-release (0.1.0-next): APIs may still change">
`create-strutvane` is implemented and tested at version `0.1.0-next.0`. It isn't on npm yet, and flags may still change before `0.1.0`.
</Aside>

## What it does

`create-strutvane` creates a new project folder for you. It asks what you're building, which database you want, how people sign in and which extras you need, then writes everything: code folders, config, `.env` with fresh secrets, local services and a CI workflow.

## Install

You don't install it. You run it once, with your package manager's `create` command:

```bash
npm create strutvane@next
```

<Aside type="note">
Coming to npm shortly as a pre-release (`0.1.0-next.0` under the `next` tag); the rest of the packages it installs are already published. Use `@next`, because the `latest` tag still points at an empty name placeholder until 1.0.
</Aside>

## Example: a full app, no questions asked

Every question also has a flag, so you can skip the prompts:

```bash
npm create strutvane@next acme -- --preset full --db postgres --auth email,google --tenancy --yes
cd acme
pnpm install
pnpm services:up     # start the local Postgres in Docker
pnpm sv migrate
pnpm sv db:seed
pnpm dev
```

## Presets

| Preset | What you get |
|---|---|
| `full` (the default) | REST API, database, sign-in and a generated React UI |
| `api` | REST API, database and background work (no `web/` folder) |
| `ui` | Screens for an API that **already exists** (no `app/` folder, no database) |

## Options

| Flag | Values | Default |
|---|---|---|
| `[folder]` | Where to create the project; its name becomes the package name | asked |
| `--preset` | `full`, `api`, `ui` | `full` |
| `--db` | `postgres`, `mysql`, `sqlite`, `azure-postgres`, `azure-mysql` | `postgres` |
| `--auth` / `--no-auth` | Comma-separated: `email`, `magic-link`, `google`, `microsoft`, `github`, or `none` | `email` |
| `--tenancy` / `--no-tenancy` | Multi-tenancy in a shared database (needs sign-in) | off |
| `--extras` / `--no-extras` | `queue`, `cache`, `mail`, `audit`, `otel`, `logs`, or `none` | `logs` |
| `--docker` / `--no-docker` | `local` (git-ignored), `commit` or `off` | `local` when there's something to run |
| `--pm` | `pnpm`, `npm`, `yarn`, `bun` | the one you ran it with |
| `--no-git` | Skip `git init` and the first commit | git on |
| `--install` | Install dependencies afterwards | off |
| `-y`, `--yes` | Accept the defaults; never ask | |
| `--dry-run` | Print the file tree and a full diff; write nothing | |

<Aside type="note" title="Planned parts of a generated project">
The starter can already write projects for every option above, but some options depend on features that aren't built yet: MySQL and Azure databases, the magic-link and social sign-in methods, and the queue, cache and mail extras. See the [roadmap](../../community/roadmap/).
</Aside>

## What gets generated

Only what your choices need. A `full` project looks like this (see [Project structure](../../concepts/project-structure/)):

```text
acme/
├─ app/                 models, policies, services, routes, jobs, providers
├─ config/              typed settings that read the validated environment
├─ database/            migrations, seeders, factories
├─ web/                 Vite + React shell around @strutvane/ui
├─ tests/               unit, feature and end-to-end tests
├─ storage/             logs and uploads (git-ignored)
├─ docker/compose.yaml  local services only (git-ignored by default)
├─ env.ts, env.schema.ts   every environment variable, validated at start-up
├─ .env                 your local values and generated secrets (git-ignored)
├─ .env.example         every key, documented, with no secrets (committed)
├─ strutvane.config.ts  which Strutvane packages are active
└─ package.json, tsconfig.json, biome.json, README.md, CLAUDE.md, .github/workflows/ci.yml
```

## Safety promises

- **Never overwrites.** The target folder must be missing or empty. That's checked before any question.
- **All or nothing.** If writing fails halfway, every file is rolled back.
- **Secrets stay secret.** `APP_KEY`, `AUTH_SECRET`, `DB_PASSWORD` and `SEED_ADMIN_PASSWORD` are generated straight into `.env`. Only the first admin password is printed, once, because you need it to sign in. `.env.example` never contains a secret.
- **Docker is local-only.** `docker/compose.yaml` binds every port to `127.0.0.1` and is git-ignored unless you pass `--docker=commit`.
- **Ctrl+C is safe.** Cancelling at any question creates nothing.
