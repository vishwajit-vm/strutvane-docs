## What it does

Think of **LEGO bricks**. Bricks from different sets fit together because they all use the same studs. `@strutvane/contracts` defines those studs.

`@strutvane/framework`, `@strutvane/auth` and `@strutvane/ui` **never import each other**. They all speak these shared definitions instead, so each works alone and all of them work together.

## What's inside

| Contract | In plain words |
|---|---|
| `Actor`, `Permission` | Who is making the request, and permission names like `"invoice.approve"` |
| `TenantContext` | Which customer company (tenant) the request belongs to |
| `QueryFilter` | A portable "which rows?" description, shared by permission rules, UI filters and SQL |
| `ListQuery`, `ListResult` | How a client asks for a page of records, and what comes back |
| `PermissionProvider`, `Decision` | What auth implements and the framework calls. Deny by default. |
| `Problem`, `ValidationIssue` | The one shape of every API error, with a stable `code` and `issues` for each field |
| `ResourceManifest` | A description of every resource, which the UI reads to build screens |
| `Logger`, `LogRecord` | The logging interface every package uses |
| `StorageDisk`, `StoredFile` | The file storage interface |
| `AuditEvent`, `DomainEvent` | "Who changed what" records, and business events like `invoice.sent` |
| `Installer`, `FieldType` | Extension points for `sv add <package>` and custom field types (draft) |
| `StandardSchemaV1` | Lets any validator (Zod, Valibot, ArkType…) plug in |

**Promises:** zero runtime dependencies (types plus a few tiny constants), strict semantic versioning, and type tests that prove misuse **fails to compile**, such as comparing with `null` or a permission without a dot.

## When you need it

Mostly indirectly: it comes with every other package. You'll import it yourself when you write a plugin, or connect your own code to a Strutvane package.

## Example: a filter and a tiny permission provider

```ts
import type { Actor, PermissionProvider, QueryFilter } from '@strutvane/contracts'

// "Invoices I own that are not void": one filter, usable in SQL and in memory.
const mine: QueryFilter = {
  op: 'and',
  filters: [
    { op: 'eq', field: 'ownerId', value: { $actor: 'id' } },
    { op: 'ne', field: 'status', value: 'void' },
  ],
}

// A deliberately simple permission provider. Real apps use @strutvane/auth.
export const adminsOnly: PermissionProvider = {
  async can(actor: Actor | null) {
    const allowed = actor?.roles.includes('admin') ?? false
    return { allowed, reason: allowed ? 'allow:role=admin' : 'default-deny' }
  },
  async filterFor(actor: Actor | null): Promise<QueryFilter> {
    return actor?.roles.includes('admin') ? { op: 'true' } : { op: 'false' }
  },
}
```

<Aside type="tip" title="NULL rules, spelled out">
`ne` also matches rows with **no value**, so "status is not void" includes rows without a status. The rules are written down, so the in-memory check and the database query always pick the same rows.
</Aside>
