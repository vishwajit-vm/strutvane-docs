## What it does

- **Permission policies:** rules like "managers can approve invoices up to 10,000", written once in TypeScript. The same rule checks one record in memory **and** filters a whole list in SQL, so nothing leaks into lists. See [Auth and permissions](../../concepts/auth-and-permissions/).
- **Deny by default:** if no rule allows something, it's not allowed, and a `deny` always beats an `allow`.
- **Multi-tenancy:** finds the current tenant (customer company) from the subdomain, path, header or session, and locks each tenant's rows away with PostgreSQL **row-level security**. See [Multi-tenancy](../../concepts/multi-tenancy/).
- **Sign-in engines:** a hardened adapter for [Better Auth](https://www.better-auth.com/) (email and password, sessions, password reset, rate limits), plus a simple in-memory engine for development and tests.
- **Middleware** for Hono and for `node:http` / Express, which turns each request into an **actor** (who is calling) and a tenant.
- **Audit records:** "who changed what", with passwords and secrets redacted.

It works **on its own** in any Node.js app, or **together** with [`@strutvane/framework`](../framework/), which only talks to it through the shared `PermissionProvider` contract.

## Example: a policy that compiles to SQL

```ts title="app/policies/invoice.policy.ts"
import { createPermissionProvider, definePolicy, defineSchema } from '@strutvane/auth'
import { compileToSql } from '@strutvane/auth/sql'

// Which columns the rules may use, and their database names and types.
const invoice = defineSchema({
  table: 'invoices',
  columns: {
    ownerId: { column: 'owner_id', type: 'uuid' },
    amount: { column: 'amount', type: 'int4' },
    status: { column: 'status', type: 'text' },
    internalNotes: { column: 'internal_notes', type: 'text' },
  },
})

export const invoicePolicy = definePolicy('invoice', { schema: invoice }, ({ allow, deny, field }) => {
  allow(['viewAny', 'view'], { role: ['accountant', 'manager'] })
  allow(['view', 'update'], { when: ({ actor, row }) => row.ownerId.eq(actor.id) })
  allow('approve', { role: 'manager', when: ({ row }) => row.amount.lte(10_000) })
  deny('delete', { when: ({ row }) => row.status.eq('paid'), name: 'paid-is-final' })
  field('internalNotes').readable({ role: 'manager' })
})

const permissions = createPermissionProvider([invoicePolicy])

// One record, in memory:
await permissions.can(actor, 'invoice.update', { type: 'invoice', record })

// A whole list, in SQL:
const filter = await permissions.filterFor(actor, 'invoice.view', 'invoice')
const where = compileToSql(filter, invoice, { alias: 'i' })
await pool.query(`SELECT * FROM invoices i WHERE ${where.sql} LIMIT 50`, where.params)
```

A typo like `row.amout`, or comparing a number with text, **doesn't compile**. Values always travel as SQL parameters, never inside the SQL text.

<Aside type="tip" title="Using the framework?">
You don't need to write the schema by hand. `policySchema(Invoice)` from `@strutvane/framework` builds it from your model: `definePolicy('invoice', { schema: policySchema(Invoice) }, …)`.
</Aside>

## Example: sign-in and tenants on a Hono server

```ts title="app/server.ts"
import { Hono } from 'hono'
import { sessionResolver } from '@strutvane/auth'
import { createBetterAuthEngine } from '@strutvane/auth/better-auth'
import { type AuthVariables, authMiddleware } from '@strutvane/auth/hono'
import { postgresRateLimitStore } from '@strutvane/auth/postgres'

const engine = createBetterAuthEngine({
  pool,
  baseURL: 'https://app.example.com',
  secret: env.AUTH_SECRET,                       // 32+ random characters, never in code
  rateLimitStore: postgresRateLimitStore(pool),  // shared by every server process
  trustedProxies: ['10.0.0.0/8'],                // only these may set X-Forwarded-For
  deliverPasswordReset: ({ email, token }) => mailer.sendReset(email, token),
  onUnexpectedError: (context, error) => logger.error(context, { err: error }),
})

const app = new Hono<{ Variables: AuthVariables }>()
app.use(authMiddleware({ engine, tenancy: { resolvers: [sessionResolver()] } }))
app.get('/me', (c) => c.json(c.get('actor')))
```

For the database lock, `tenantRlsSql({ table: 'app.invoices', runtimeRole: 'app_user' })` writes the row-level security SQL for a migration, and `withTenant(pool, tenantId, fn)` runs queries inside one tenant. Both come from `@strutvane/auth/postgres`.

## Entry points

| Import | What it gives you |
|---|---|
| `@strutvane/auth` | `definePolicy`, `defineSchema`, `createPermissionProvider`, tenant resolvers, `recordAudit`, `createNativeEngine` |
| `@strutvane/auth/sql` | `compileToSql` |
| `@strutvane/auth/postgres` | `withTenant`, `tenantRlsSql`, `tenancyAudit`, `postgresRateLimitStore` |
| `@strutvane/auth/better-auth` | `createBetterAuthEngine` |
| `@strutvane/auth/hono`, `@strutvane/auth/node` | `authMiddleware` for Hono, and for `node:http` / Express |
| `@strutvane/auth/testing` | A test suite any sign-in engine must pass, plus helpers |

## Planned, not available yet

- The ready-made sign-in API (`/api/v1/auth/*`), the sign-in screens, the `sv add auth` installer and the `sv auth:*` commands
- Single sign-on (OIDC and SAML), SCIM, two-factor authentication and passkeys, magic links, social sign-in, API keys and JWT refresh
- Schema-per-tenant and database-per-tenant (today: one shared database with row-level security)
- A PostgreSQL audit store with a tamper-evident hash chain (today: an in-memory store and the `AuditSink` interface)
- Dedicated Fastify and NestJS adapters (Express already works through `@strutvane/auth/node`)
