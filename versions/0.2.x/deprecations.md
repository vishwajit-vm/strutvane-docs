A **deprecated** API still works, but it's on its way out: the docs name its replacement, and it's removed in a later line. Before anything is removed from Strutvane, it's deprecated for at least one full line, so you always have a release in which the old and the new both work. This page lists every deprecation in the 0.2 line of `@strutvane/framework` (0.2.0-next.0). The packages retired in 0.2, each with its replacement, are in the [release notes](../releases/), and the rules are on [Versioning & Support](../versioning/).

:::tip[Coming from Laravel?]
It's Laravel's approach: deprecated in one release, removed in the next major (before 1.0, each `0.N` line plays the role of a major). Your editor shows a deprecated function struck through, from its `@deprecated` tag. Runtime warnings are Node's own `DeprecationWarning`s, printed once per process, so `node --no-deprecation` hides them and `node --throw-deprecation` turns them into errors in CI.
:::

## The list

| Deprecated in 0.2 | Use instead | How you notice | Removed in |
|---|---|---|---|
| Uppercase error codes (`NOT_FOUND`, `VALIDATION_FAILED`, …), the framework's and your app's own | The lowercase `snake_case` names (`not_found`, `validation_failed`) | A `STRUTVANE_UPPERCASE_ERROR_CODE` warning at runtime | 0.3 |
| Model-first migration planning (Drizzle-based): `planMigration`, `classifyChanges`, `describeRename`, `assertPromptFree`, `RenameResolutionRequiredError`, `DestructiveChangeError`, `renderMigration`, `answersResolver`, `writeMigration`, `readSnapshot`, `migrateProject`, `compilePg`, `compileSqlite`, `defaultNaming`, `shortenIdentifier` | Columns in migrations with the Schema builder, then `node strut migrate` ([Migrations](../migrations/)) | `@deprecated` in your editor | 0.3 |
| The 0.1 custom-route builders `route.get()`, `route.post()`, `route.put()`, `route.patch()` and `route.delete()` (for `createHttpApp`) | `Route.get()` and friends in a routes file ([Routing](../routing/)) | `@deprecated` in your editor | 0.3 |

0.1-style apps (models declared with `defineModel` in `app/models/*.model.ts`) keep working in 0.2: the database commands detect them and take the 0.1 path. The planning functions above are what that path is built on, which is why they go away together in 0.3.

## Lowercase error codes

Every error code is lowercase `snake_case` from 0.2: HTTP problem codes, the codes of `node strut … --json`, and the codes of the container, the devkit and the model DSL. Each new name is the old one in lower case. Through the 0.2 line the old names keep working:

```ts title="scripts/legacy-code.ts"
import { LEGACY_ERROR_CODES, StrutvaneError } from '@strutvane/framework/core'

const error = new StrutvaneError('NOT_FOUND', { status: 404 })
console.log(error.code)                              // → 'not_found'
console.log(LEGACY_ERROR_CODES['VALIDATION_FAILED'])  // → 'validation_failed'
```

**What you'll see** the first time an old name is used in a process:

```text
(node:1234) [STRUTVANE_UPPERCASE_ERROR_CODE] DeprecationWarning: Error code "NOT_FOUND" was renamed to "not_found" in @strutvane/framework 0.2; the old name stops working in 0.3. Use "not_found".
```

Your app's own uppercase code (`INVOICE_ALREADY_PAID`) is still accepted in 0.2, with this warning:

```text
(node:1234) [STRUTVANE_UPPERCASE_ERROR_CODE] DeprecationWarning: Error code "INVOICE_ALREADY_PAID" is uppercase; Strutvane codes are lowercase snake_case from 0.2 ("invoice_already_paid"). Uppercase codes stop being accepted in 0.3.
```

`LEGACY_ERROR_CODES` is the full table of renames. Clients that compare `problem.code` must switch to the lowercase names, and message catalog keys become `errors.<new code>.title`. See [Error Handling](../errors/#error-codes-are-lowercase).

## Model-first migration planning

In 0.1, migrations were generated by comparing `defineModel` files with a snapshot. In 0.2, **migrations are the source of truth**: you write the columns with the Schema builder, and the types are generated from the migrations.

```ts title="database/migrations/2026_11_18_093000_create_posts_table.ts"
import { migration } from '@strutvane/framework/schema'

export default migration({
  up(schema) {
    schema.create('posts', (t) => {
      t.id()
      t.string('title', 200)
      t.timestamps()
    })
  },
  down(schema) {
    schema.dropIfExists('posts')
  },
})
```

```bash
node strut migrate
```

Move each 0.1 model's columns into a `create_<table>_table` migration (`node strut make:migration create_posts_table` writes the migration and the new model), then delete the old model file. The [upgrade guide](../upgrade/#columns-move-from-models-to-migrations) walks through it.

## Common mistakes

### I see `STRUTVANE_UPPERCASE_ERROR_CODE` in my test output

```text
DeprecationWarning: Error code "NOT_FOUND" was renamed to "not_found" in @strutvane/framework 0.2; the old name stops working in 0.3. Use "not_found".
```

**Why:** some code (yours, or a test) still uses an old uppercase code, in `new StrutvaneError('NOT_FOUND')` or in a comparison.

**Fix:** use the lowercase name the warning gives. To find every place, run the tests once with `node --throw-deprecation`, so the first use fails with a stack trace.

### My client still checks `problem.code === 'NOT_FOUND'`

**Why:** the server sends `not_found` from 0.2; only server-side code gets the compatibility layer.

**Fix:**

```ts title="resources/ui/api/errors.ts"
export function isNotFound(problem: { code: string }): boolean {
  return problem.code === 'not_found'
}
```
