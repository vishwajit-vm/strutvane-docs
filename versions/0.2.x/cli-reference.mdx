`node strut` is your app's **command line**: the small program you type commands into to create files, run migrations, inspect routes and look after your app. It's Strutvane's `php artisan`. It works the same in PowerShell, cmd, bash and zsh.

```bash
node strut <command> [arguments] [flags]
```

An **argument** is a value the command needs, like the name in `make:migration create_posts_table`. A **flag** (or option) starts with `--` and changes what the command does, like `--json`.

This page lists **every** command of Strutvane 0.2, grouped the way Laravel groups artisan's commands. The command line ships inside `@strutvane/framework`, so its version is the framework's. Each command has a status:

| Status | Meaning |
|---|---|
| **Available** | In `@strutvane/framework` 0.2.0-next.0 (the framework's `main` branch; not on npm yet). The output on this page is copied from a real run. |
| **Listed, not built** | `node strut list` shows it, but running it stops with a message instead of pretending to work (see [Commands that aren't built yet](#commands-that-arent-built-yet)). |
| **Coming in 0.2** | Designed for 0.2, not in the framework yet, or provided by another 0.2 package (the installer, `@strutvane/auth`, `@strutvane/ui`). Output is "something like this". |
| **0.3**, **Before 1.0** | Planned for a later release (queues, the scheduler and cache drivers in 0.3; charts before 1.0). |

:::tip[Coming from Laravel?]
The names are artisan's: `php artisan route:list` → `node strut route:list`, `php artisan migrate` → `node strut migrate`, `php artisan make:command` → `node strut make:command`, `php artisan down` → `node strut down`.

Differences: every command accepts `--json` for scripts and AI agents; destructive commands (`migrate:fresh`, `key:rotate`…) refuse to run outside local and test environments unless you add `--force --i-understand`; and `npx strutvane <command>` does exactly the same as `node strut <command>`.
:::

## The smallest example

```bash
node strut list
```

**What you'll see** (shortened; from a real run in a new app):

```text
strutvane 0.2.0-next.0: the Strutvane command line

Usage: node strut <command> [arguments] [flags]

Commands:
  about        Show versions of the CLI, Node.js and installed Strutvane packages
  add          Install a package and run its installer (config, env, routes, migrations…)
  build        Check that the app boots (models, config, routes) and build the web UI with Vite
  dev          Serve the API and the web UI (the project's Vite, with HMR) on one port; restart on app/, config/ or .env changes
  doctor       Diagnose Node.js, the project, env files, the registry and plugins
  down         Put the application into maintenance mode
  migrate      Diff models with the database, write a migration and apply it
  start        Start the app server (the API, and the built UI from dist/web when present)
  sync         Regenerate .strutvane/ (types, resources.json, schema.json, SQL) from the migrations
  up           Bring the application out of maintenance mode

make:
  make:command    Create a console command in app/console/commands
  make:migration  Create a migration (and, for create_*_table, its model)

route:
  route:list   List every route of the app (--security: protections, opt-outs, warnings)

Run `node strut help <command>` for details. Colon names also work with spaces: `node strut make model`.
```

`list` is the command; `help` with no command name is an alias of it, and so is `node strut` on its own. The real list is longer: every command on this page that is **Available** or **Listed, not built** appears there, plus your app's own commands.

## Where commands come from

`node strut` merges three sources, so one list shows everything:

1. **Built-in commands**, which ship with the framework (`make:*`, `route:list`, `down`…).
2. **Commands of installed packages.** A package declares a commands module in its `package.json` (`"strutvane": { "commands": "./dist/commands.mjs" }`). The framework itself contributes `migrate`, `db:seed`, `start`, `dev`, `build` and `sync` this way. A package whose `strutvane.compat` range doesn't match your framework version is skipped, and `node strut doctor` says why.
3. **Your app's commands**, registered in `bootstrap/app.ts` with `.withCommands([...])`. See [Strut Console](../strut-console/) to write one.

A command from a package or from your app with the same name as a built-in one replaces it.

**Shortcuts.** A command group on its own lists the group (`node strut make`). Colon names also work with spaces (`node strut make migration create_posts_table`). An unambiguous abbreviation runs the command (`node strut m:st` runs `migrate:status`), except for destructive commands, which must be typed in full.

## Flags every command accepts

| Flag | What it does |
|---|---|
| `--json` | Print one JSON document instead of text, for scripts and AI agents |
| `--dry-run` | Show what would happen; write nothing |
| `--diff` | Show a unified diff of file changes |
| `-y`, `--yes` | Accept all defaults; never prompt |
| `--interactive` | Prompt for missing input (`--no-interactive` fails instead) |
| `--force` | Overwrite generated files you haven't taken over; also half of `--force --i-understand` for destructive commands |
| `--cwd <path>` | Run as if in another folder |
| `--env <name>` | Load `.env.<name>` over `.env` (for example `--env=testing`) |
| `-v`, `--verbose` | Debug logging and stack traces |
| `-q`, `--quiet` | Only print results and errors |
| `--color`, `--no-color` | Force colours on or off |
| `-h`, `--help` | Show the help of a command (`node strut migrate --help`) |

With `--json`, every command prints the same envelope. For example `node strut posts:report ada --json`, an app command from [Strut Console](../strut-console/):

```json
{
  "schemaVersion": 1,
  "ok": true,
  "command": "posts:report",
  "exitCode": 0,
  "data": {
    "author": "ada",
    "format": "text"
  },
  "warnings": []
}
```

## General

### list and help

```bash
node strut list
node strut help make:migration
node strut make:migration --help     # the same
```

**What you'll see** for `help make:migration`:

```text
make:migration

Create a migration (and, for create_*_table, its model)

Migration-first apps: create_posts_table creates a table and app/models/post.ts; add_x_to_posts_table alters one; any other name gets a blank migration. --seeder adds the seeder and its factory and registers the seeder in database/seeders/database.seeder.ts; --factory adds only the factory. v1 apps (strutvane.config.ts, no Laravel-named migrations) get a hand-written stub.

Usage: node strut make:migration <name> [flags]

Arguments:
  name  snake_case, e.g. create_posts_table or add_subtitle_to_posts_table

Flags:
  --seeder         Also create the seeder and its factory, and register the seeder
  --factory        Also create the factory
  --sql            v1 apps: a raw .sql file instead of TypeScript
  --table <table>  v1 apps: pre-fill an ALTER TABLE statement for this table

Global flags: --json --dry-run --diff --yes --force --cwd <path> --no-color (node strut help)

Examples:
  node strut make:migration create_posts_table --seeder
  node strut make:migration add_subtitle_to_posts_table
```

`<name>` is required; `[name]` would be optional. Flags with a value take it as `--table=posts` or `--table posts`.

### about

```bash
node strut about
```

**What you'll see:**

```text
@strutvane/framework  0.2.0-next.0
Node.js               24.21.0
Platform              win32 x64
Project               my-blog (C:\projects\my-blog)
Package manager       npm

Package               Declared      Installed
@strutvane/framework  0.2.0-next.0  0.2.0-next.0
```

It never prints secrets, so it's safe to paste into a bug report. `--json` prints the same as JSON.

### doctor

```bash
node strut doctor
```

Checks your setup and gives a fix for each problem: the Node.js version (24.3 or newer), `"type": "module"` in `package.json`, that `@strutvane/framework` is a dependency (and that none of the old part packages it replaced is installed), `.env` against `.env.example`, whether the registry is up to date, and whether each installed Strutvane package could be loaded. `--global` checks only the environment, so it needs no project.

**What you'll see** (the lines depend on your project):

```text
✔ Node.js 24.21.0
✔ package.json has "type": "module"
✔ @strutvane/framework is a project dependency
✔ No package that @strutvane/framework replaced is installed
✔ 1 Strutvane package(s) installed
! No .env.example
  Document every variable the app reads in .env.example.
✔ The registry is up to date
```

A failed check is marked `✖`, with the fix on the next line, and the command exits with code `3`.

### env:check

```bash
node strut env:check
node strut env:check --strict
```

Compares `.env` with `.env.example`. It exits with code `3` when a documented key is missing, a line is invalid, or a secret-looking key has a value in `.env.example`. `--strict` also treats unknown and empty keys as errors. Values are never printed, and malformed lines are reported by file and line number only.

### dev

```bash
npm run dev          # the same as: node strut dev
```

Serves your app for development: the API and, when your project has a `vite.config.*` and Vite installed, the web UI through your own Vite with hot reload, **on one port**. It restarts when `app/`, `config/` or `.env` change. Without Vite it serves the API only and says so.

| Flag | Default | What it does |
|---|---|---|
| `--port <value>` | `APP_PORT` | The port |
| `--host <value>` | `127.0.0.1` | The interface to listen on |

The server answers only your own host names (`localhost`, `127.0.0.1`, `[::1]`, `APP_URL`'s host and `config/app.ts` `trustedHosts`), so a web page you visit can't reach it through a DNS trick. A port that's taken stops `dev` with an error that names the port: change `APP_PORT` or pass `--port`.

### start

```bash
node strut start --port=3000
```

Boots `bootstrap/app.ts` **before** the port opens, so a broken route or a weak key never starts serving, then serves the API, and the built UI from `dist/web` when it exists.

**What you'll see:**

```text
✔ Listening on http://127.0.0.1:3000 (APP_ENV=local)
```

It takes the same `--port` and `--host` flags as `dev`. <kbd>Ctrl</kbd>+<kbd>C</kbd> stops the server and lets work it deferred until after a response finish first.

### build

```bash
npm run build        # the same as: node strut build
```

Checks that the app boots (models, config, routes), then builds the web UI with your project's Vite into `dist/web`, which `start` serves.

### test and setup

:::caution[Coming in 0.2]
`npm test` and `npm run setup` are scripts the installer (`create-strutvane`) writes into your project; they aren't `node strut` commands in the framework. `npm test` runs `vitest run`. `npm run setup` resumes an installer run that stopped part-way (for example because Docker wasn't running). See [Installation](../installation/) and [Testing](../testing/).
:::

## Make

`make:*` commands write new files into your project. They never overwrite a file you changed unless you pass `--force`; running one again on an untouched file reports `Nothing to do`. `--dry-run --diff` shows what would change.

### make:migration

```bash
node strut make:migration create_posts_table --seeder
```

**What you'll see:**

```text
  create    database/migrations/2026_11_18_015306_create_posts_table.ts
  create    app/models/post.ts
  create    database/factories/post.factory.ts
  create    database/seeders/post.seeder.ts
  create    database/seeders/database.seeder.ts
✔ migration-first: 5 file(s) written.
Next: node strut migrate
```

| Argument / flag | What it does |
|---|---|
| `<name>` | snake_case. `create_posts_table` creates a table and its model, `add_subtitle_to_posts_table` alters one, anything else gets an empty migration |
| `--seeder` | Also create the seeder **and** its factory, and register the seeder in `database/seeders/database.seeder.ts` |
| `--factory` | Also create the factory, and only the factory |
| `--sql`, `--table <table>` | For 0.1-style apps only: a raw `.sql` file, or an `ALTER TABLE` stub for that table |

The migration is named with the current time (UTC), so migrations always run in order. The model it writes imports `Model` from `@strutvane/framework/database` and starts with an empty `fillable` list. See [Migrations](../migrations/) and [Seeding](../seeding/).

### make:command, make:rule and make:observer

```bash
node strut make:command SendReports
node strut make:command SendReports --command=reports:send
node strut make:rule Slug
node strut make:observer PostObserver --model=Post
```

**What you'll see** for `make:command SendReports`:

```text
  create app/console/commands/send-reports.command.ts
Next: register it in bootstrap/app.ts with .withCommands([sendReportsCommand]), then run node strut app:send-reports
```

| Command | Writes | Flags |
|---|---|---|
| `make:command <name>` | `app/console/commands/<name>.command.ts`, run as `app:<name>` | `--command <name>`: the name to run it by |
| `make:rule <name>` | A validation rule in `app/rules` | none |
| `make:observer <name>` | A model observer in `app/observers`, with `created`, `updated`, `deleted`, `restored` and `forceDeleted` methods | `--model <Model>`: the model it observes (default: from the name) |

Model events aren't built yet, so an observer has nothing to attach to; see [Events & Observers](../orm-events/).

### The 0.1-style generators

`make:model`, `make:resource`, `make:policy`, `make:seeder`, `make:factory` and `make:test` exist, but they still write the file shapes of 0.1-style apps (models declared with `defineModel` in `app/models/*.model.ts`). In a migration-first app, use `make:migration … --seeder` instead, which writes the model, the factory and the seeder in their 0.2 shapes.

| Command | Arguments and flags |
|---|---|
| `make:model <name> [fields]...` | `--all`, `--policy`, `--factory`, `--seeder`, `--test`, `--api`, `--ui` (all on by default except `--all`), `--tenant`, `--audit`, `--soft-deletes`, `--timestamps`, `--seed <count>` (default 10) |
| `make:resource <model>` | `--actions <list>`, `--hooks <list>` |
| `make:policy <model>` | `--template <name>` (default `default`) |
| `make:seeder <name>` | `--model <name>`, `--count <n>` (default 10) |
| `make:factory <model>` | none |
| `make:test <name>` | `--unit`, `--e2e`, `--model <name>` |

### make:controller and make:request

:::caution[Coming in 0.2]
Not in `@strutvane/framework` 0.2.0-next.0: `node strut make:controller` answers `Unknown command "make:controller"`. Write the class by hand for now; [Controllers](../controllers/) and [Requests](../requests/) show complete files.
:::

## Database

The database commands read the `DB_*` settings from `.env` (see [Database](../database/)) and print the connection they use first, like `Database: sqlite:C:\projects\my-blog\database\database.sqlite`.

### migrate

```bash
node strut migrate
```

Runs every migration that hasn't run yet (each one is recorded in the `migrations` table, in a numbered **batch**), then regenerates the files in `.strutvane/` from your migrations.

**What you'll see:**

```text
Database: sqlite:C:\projects\my-blog\database\database.sqlite
✔ Migrated 2026_11_18_015306_create_posts_table (batch 1)
Updated .strutvane/resources.json
Updated .strutvane/schema.json
Updated .strutvane/sql/migrations.mariadb.sql
Updated .strutvane/sql/migrations.mysql.sql
Updated .strutvane/sql/migrations.postgres.sql
Updated .strutvane/sql/migrations.sqlite.sql
Updated .strutvane/sql/schema.mariadb.sql
Updated .strutvane/sql/schema.mysql.sql
Updated .strutvane/sql/schema.postgres.sql
Updated .strutvane/sql/schema.sqlite.sql
Updated .strutvane/types/models.d.ts
```

| Flag | What it does |
|---|---|
| `--pretend` | Print the SQL the pending migrations would run; change nothing |
| `--step` | One batch per migration, so they roll back one at a time |
| `--seed` | Run `database/seeders/database.seeder.ts` afterwards |
| `--force` | Allow changing the database when `APP_ENV` is `production` |
| `--isolated` | Don't wait when another `migrate` holds the lock: report it and do nothing |

`--name`, `--allow-destructive`, `--rename` and `--separate` also appear in `node strut help migrate`. They belong to 0.1-style apps, whose migrations are generated from `defineModel` files.

**What you'll see** for `migrate --pretend`:

```text
Database: sqlite:C:\projects\my-blog\database\database.sqlite
-- 2026_11_18_015306_create_posts_table
CREATE TABLE "posts" (
  "id" INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  "created_at" DATETIME NULL,
  "updated_at" DATETIME NULL
);
```

Each migration is first replayed in a **sandbox** (a separate, locked-down Node process with no secrets and no network), so a migration file can't read your `.env` or call out. See [Migrations](../migrations/) for the rules.

### migrate:status

```bash
node strut migrate:status
```

**What you'll see:**

```text
Database: sqlite:C:\projects\my-blog\database\database.sqlite
Migration                             Status
2026_11_18_015306_create_posts_table  ran (batch 1)
```

It also reports **drift**: a migration that ran and was edited afterwards, or one that's recorded in the database but missing from `database/migrations/`. It exits with code `1` when there is drift.

### migrate:rollback, migrate:reset, migrate:refresh and migrate:fresh

```bash
node strut migrate:rollback             # undo the last batch
node strut migrate:rollback --step=2    # undo the last two migrations
node strut migrate:rollback --batch=3   # undo batch 3
node strut migrate:reset                # undo every migration
node strut migrate:refresh --seed       # undo everything, migrate again, seed
node strut migrate:fresh --seed         # drop every table, migrate again, seed
```

| Command | Flags |
|---|---|
| `migrate:rollback` | `--step <n>`, `--batch <n>`, `--pretend`, `--force`, `--isolated` |
| `migrate:reset` | `--force`, `--isolated` |
| `migrate:refresh` | `--seed`, `--force`, `--isolated` |
| `migrate:fresh` | `--seed`, `--force`, `--isolated` |

:::danger[These commands delete data]
All four are **destructive**. They run without a question only when `APP_ENV` is `local`, `test`, `testing` or `development`. Anywhere else, including when `APP_ENV` isn't set, they stop unless you add `--force --i-understand`, and they must be typed in full (no abbreviations). See [Destructive commands](#destructive-commands).
:::

### sync

```bash
node strut sync
```

Regenerates `.strutvane/` (the types in `types/models.d.ts`, `resources.json`, `schema.json` and the per-engine SQL) from your migrations, without touching the database. `migrate` does this for you; `sync` is for when the generated files are missing or stale, for example after resolving a merge conflict in them.

**What you'll see:**


Runs `database/seeders/database.seeder.ts`, which calls the other seeders in order.

## Inspect

### route:list

Shows every route of the app, in the order they're matched. It boots the app first, so it's also the quickest check that the app starts.

| Flag | What it does |
|---|---|
| `--path <text>` | Only URIs containing this text |
| `--name <text>` | Only names containing this text |
| `--method <METHOD>` | Only this HTTP method |
| `--security` | Show the protections, opt-outs and warnings of each route |
| `--force-debug` | Boot even with `APP_DEBUG=true` in production |

```bash
node strut route:list
```

**What you'll see** (a new app with one API route and one web route):

```text
Method  URI                     Name                  Action   Middleware
GET     /                       home                  Closure  csrf
GET     /api/hello              hello                 Closure  csrf, throttle:api
POST    /_strutvane/csp-report  strutvane.csp-report  Closure  throttle:60:1
GET     /up                                           Closure

  Showing 4 of 4 routes.
```

`/_strutvane/csp-report` receives the browser's Content Security Policy reports, and `/up` is the health check. See [Routing](../routing/).

#### Seeing the security of every route

`--security` replaces the middleware column with the **protections** that really apply to each route, after groups, the route itself, the controller and handler wrappers have all been taken into account. Every **opt-out** (a protection someone switched off) is listed with where it was switched off, and an unsafe route with no CSRF check at all is a warning.

```bash
node strut route:list --security
```

**What you'll see:**

```text
Method  URI                     Name                  Protections         Opt-outs        Warnings
GET     /                       home                  csrf
GET     /api/hello              hello                 csrf, throttle:api
POST    /_strutvane/csp-report  strutvane.csp-report  throttle:60,1       ! csrf (route)
GET     /up                                           (none)

  4 routes, 1 opt-out, 0 warnings.
```

See [CSRF Protection](../csrf/) and [Security Features](../security/).

```bash
node strut event:list
node strut event:list --event=post
```

Lists every event and its listeners (discovered in `app/listeners`). See [Events](../events/).

### routes, models and permissions

`node strut routes` (`--method`, `--path`, `--model`), `node strut models` (`--model`) and `node strut permissions` (`--model`) list the CRUD routes, models and permissions that 0.1-style apps generate from their `defineModel` files. For a migration-first app, use `route:list`.

## Packages

### add, remove and upgrade

```bash
node strut add @strutvane/log-viewer
node strut remove @strutvane/log-viewer --keep-data
node strut upgrade
```

| Command | What it does | Flags |
|---|---|---|
| `add <package>` | Installs the package with npm and runs its installer (config, `.env` keys, routes, migrations…) | none |
| `remove <package>` | Reverses the package's installer, then uninstalls it. Files you edited are kept | `--keep-data` (keep its tables and stored data), `--keep-package` (only reverse the installer) |
| `upgrade` | Bumps every Strutvane package and three-way merges the files they generated, keeping your edits | `--to <version>`, `--channel <tag>` (`next`, `canary`…), `--no-typecheck` (skip the `tsc --noEmit` run afterwards) |

### registry:build and registry:watch

```bash
node strut registry:build --check
node strut registry:watch
```

They compile your app's conventions (the files under `app/` and `web/`) into the typed `.strutvane/registry.gen.ts`. `--check` writes nothing and exits with code `6` when the file is stale, for CI. `registry:watch` rebuilds on every change (`--debounce <ms>`, default 25); <kbd>Ctrl</kbd>+<kbd>C</kbd> stops it.

### install:name

:::caution[Coming in 0.2]
Designed, not built yet: `node strut install:<name>` installs one package by its short name and runs its installer, with the same result in any order. Today, `node strut add <package>` does this. See [Package Catalogue](../packages/catalogue/).
:::

## Maintenance mode

### down and up

```bash
node strut down --secret=team-preview-2026 --retry=60
```

**What you'll see:**

```text
✔ The application is now in maintenance mode.
  Bypass it by visiting http://localhost/team-preview-2026 (shown once; the secret is not stored).
```

`down` puts the app in **maintenance mode**: every process serving the app answers `503` from its next request, until you run `up`. The health route `/up` keeps answering `200`, so a load balancer doesn't drop the server. The bypass secret is never stored (only an HMAC under an `APP_KEY` subkey), and a new `down` invalidates every earlier bypass cookie.

| Flag | What it does |
|---|---|
| `--secret <secret>` | Visiting `/<secret>` sets a cookie that lets you use the app while it's down. 8 to 128 URL-safe characters |
| `--with-secret` | Generate a random secret and print the bypass address once |
| `--retry <seconds>` | The `Retry-After` header |
| `--refresh <seconds>` | The `Refresh` header (the browser reloads after that many seconds) |
| `--redirect <path>` | Redirect every request to this path on your own site |
| `--render <file>` | Show browsers your own `.html` file from `resources/views` |
| `--force-debug` | Boot even with `APP_DEBUG=true` in production |

```bash
node strut up
```

```text
✔ The application is now live.
```

See [Maintenance Mode](../maintenance-mode/).

## Security

### key:generate and key:rotate

```bash
node strut key:generate
node strut key:rotate
```

`key:generate` writes `APP_KEY` to `.env` (and an empty `APP_KEY=` entry to `.env.example`). It never prints the key unless you ask with `--show`, which prints a new key and writes nothing. Replacing an existing key needs `--force`, and outside local and test environments also `--i-understand`.

```text
✔ APP_KEY written to .env (and documented in .env.example).
```

`key:rotate` creates a new key and moves the old one to the front of `APP_PREVIOUS_KEYS`, so encrypted values and signed links made with the old key keep working. It's destructive.

```text
✔ New APP_KEY set; the old key is first in APP_PREVIOUS_KEYS.
  1 previous key still accepted for decryption and signed links.
  Deploy the new .env everywhere, and run node strut optimize again if you cache config.
```

See [Encryption](../encryption/#rotating-app_key).

### env:encrypt and env:decrypt

```bash
node strut env:encrypt --env=production
node strut env:decrypt --env=production
```

`env:encrypt` encrypts `.env.production` (or `.env` without `--env`) into `.env.production.encrypted`, a file you can commit. The key comes from the `STRUT_ENV_KEY` variable or `--key`; without one, a new key is generated and printed once.

```text
✔ Encrypted .env into .env.encrypted.

  Decryption key (shown once, never saved; keep it in your secrets manager or CI secrets):
  base64:…
```

`env:decrypt` reverses it on the server. Prefer `STRUT_ENV_KEY` over `--key`, because a flag lands in your shell history.

### session:flush

```bash
node strut session:flush
```

```text
✔ 3 sessions deleted. Everyone signed in with a session must sign in again.
API tokens are not affected; revoke them with the auth package.
```

Use it after an incident. It's destructive, so outside local and test environments it needs `--force --i-understand`.

### security:check

```bash
node strut security:check
node strut security:check --audit    # also runs npm audit (needs the network)
```

**What you'll see:**

```text
   Check            Detail
✔  debug            APP_DEBUG=true, APP_ENV=local
✔  app-key          APP_KEY is set and at least 32 bytes
✔  https            not production (http://localhost:3000)
✔  cookies          HttpOnly, SameSite=Lax (Secure in production)
✔  boot             every boot-time check passed (CORS, headers, hosts, proxies, limits, routes)
✔  csp              nonce-based script-src
✔  csrf-exceptions  0 exception patterns
✔  cors             off
✔  dev-tools        no /_ routes without auth
·  npm-audit        run with --audit (needs the network)

✔ No failures, 0 warnings.
```

It exits with code `3` when any check fails, so CI can block a deploy. See [Security Features](../security/).

## Destructive commands

`key:rotate`, `session:flush`, `migrate:rollback`, `migrate:reset`, `migrate:refresh` and `migrate:fresh` (and, once built, `db:wipe` and `db:restore`) can lose data or sign people out. So:

- they run without a question only when `APP_ENV` is `local`, `test`, `testing` or `development`;
- anywhere else, including when `APP_ENV` isn't set, they need `--force --i-understand`;
- they must be typed in full: `node strut migrate:f` never runs `migrate:fresh`.

`APP_ENV` is read the way the app reads it: the real environment first, then `.env.<name>` with `--env`, then `.env`.

```bash
APP_ENV=production node strut session:flush
```

```text
error `node strut session:flush` is destructive and APP_ENV is "production" (from the environment); it runs without confirmation only in local, test, testing or development.
hint: Set APP_ENV for this project, or pass --force --i-understand if you really mean it.
```

## Exit codes

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | A general failure: an unexpected error, a failed child process, migration drift |
| `2` | Invalid usage: an unknown command or flag, a bad or missing argument, a refused destructive command |
| `3` | Validation failed: a bad `.env` value, a config or boot error, failed `doctor`, `env:check` or `security:check` checks |
| `4` | Conflict: a file you changed would be overwritten |
| `5` | A database error |
| `6` | Something is pending: a stale registry with `registry:build --check` |
| `7` | Incompatible versions: a package's `strutvane.compat` range doesn't match |
| `130` | Interrupted with <kbd>Ctrl</kbd>+<kbd>C</kbd> |

Scripts and CI can rely on them: `node strut route:list || exit 1`. A code never changes meaning once released.

## Setting a variable for one command

Sometimes you want to run one command with a different setting, without editing `.env`. Real environment variables always win over `.env`:

<Tabs syncKey="os">
  <TabItem label="macOS / Linux">

```bash
APP_ENV=testing node strut route:list
```

  </TabItem>
  <TabItem label="Windows (PowerShell)">

```powershell
$env:APP_ENV='testing'; node strut route:list
```

The variable stays set for the rest of that PowerShell window. Remove it with `Remove-Item Env:APP_ENV`.

  </TabItem>
  <TabItem label="Windows (cmd)">

```bat
set APP_ENV=testing && node strut route:list
```

  </TabItem>
</Tabs>

For a whole set of values, keep them in `.env.testing` and pass `--env=testing`.

## Common mistakes

### "Unknown command"

```text
error Unknown command "make:controller".
hint: Run `node strut help` to see every command.
```

**Why:** the command is misspelled, or it doesn't exist in the framework version you're running (check its status on this page).

**Fix:** check the spelling with `node strut list`.

### "The installed @strutvane/framework does not provide …"

```text
error The installed @strutvane/framework does not provide `node strut migrate`.
hint: Run `node strut doctor` to see why its commands were not loaded (e.g. a version mismatch), then `node strut upgrade`.
```

**Why:** either the command isn't built yet (see [Commands that aren't built yet](#commands-that-arent-built-yet)), or the package that provides it couldn't be loaded, for example because its `strutvane.compat` range doesn't match your framework version.

**Fix:** run `node strut doctor`; it names the package and the reason.

### "APP_KEY is missing"

```text
error APP_KEY is missing.
  → Run `node strut key:generate` to create a strong key (32 random bytes).
```

**Why:** commands that boot the app (`route:list`, `optimize`, `start`…) check the key first, and refuse to run without a strong one.

**Fix:**

```bash
node strut key:generate
```

### "The app refuses to start: APP_DEBUG=true with APP_ENV=production"

```text
error The app refuses to start: APP_DEBUG=true with APP_ENV=production.
  → Set APP_DEBUG=false in the production environment. To start anyway for a short investigation, pass --force-debug (debug pages stay off in production either way).
```

**Why:** debug output in production leaks details about your app, so Strutvane fails closed.

**Fix:** set `APP_DEBUG=false` on the server. The commands that boot the app for a task (`route:list`, `optimize`, `down`…) accept `--force-debug` for a short investigation.

:::caution[Coming in 0.2]
`node strut start` and `node strut dev` don't accept `--force-debug` yet, although the message mentions it. Set `APP_DEBUG=false` to start the server.
:::

### "… already exists with different content"

```text
error app/console/commands/send-reports.command.ts already exists with different content; pass { overwrite: true } to replace it
hint: Pass --force to overwrite generated files, or --dry-run --diff to compare.
```

**Why:** `make:*` never overwrites a file you changed. The exit code is `4`.

**Fix:** pick another name, compare with `--dry-run --diff`, or add `--force` if you really want to replace the file.

### `npm run strut route:list -- --json` behaves oddly

**Why:** through `npm run`, npm takes flags for itself unless they come after `--`, and it prints its own lines around the output.

**Fix:** call it directly, which needs no `--`:

```bash
node strut route:list --json
```
